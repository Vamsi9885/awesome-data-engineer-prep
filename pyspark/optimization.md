# ⚙️ Spark Optimization (From Slow Jobs to Production-Grade Pipelines)

---

## 1) Concept Explanation

Spark optimization is mostly about reducing:
- data scanned
- shuffle volume
- skew impact
- serialization and Python overhead

Top optimization levers:
1. Query optimization (Catalyst, AQE)
2. Data layout optimization (partitioning, file sizing, pruning)
3. Execution optimization (join strategy, caching, config tuning)

---

## 2) PySpark Code Examples (Real-World)

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, broadcast, sum as _sum

spark = (
    SparkSession.builder
    .appName("optimization-playbook")
    .config("spark.sql.adaptive.enabled", "true")
    .config("spark.sql.adaptive.coalescePartitions.enabled", "true")
    .config("spark.sql.shuffle.partitions", "300")
    .getOrCreate()
)
```

### A) Predicate pushdown + column pruning

```python
orders = (
    spark.read.parquet("s3://lake/orders/")
    .select("order_id", "customer_id", "order_date", "amount", "status")
    .filter(col("order_date") >= "2024-01-01")
    .filter(col("status") == "COMPLETE")
)
```

### B) Broadcast join for small dimension

```python
customers = spark.read.parquet("s3://lake/dim/customers/").select("customer_id", "segment")
enriched = orders.join(broadcast(customers), "customer_id", "left")
```

### C) Cache when reused multiple times

```python
enriched.cache()

kpi1 = enriched.groupBy("segment").agg(_sum("amount").alias("gmv"))
kpi2 = enriched.groupBy("segment").count()
```

### D) Repartition before wide write (when needed)

```python
kpi1.repartition(50).write.mode("overwrite").parquet("s3://lake/marts/segment_gmv/")
```

## 3) DAG Explanation

```text
Stage 1:
  Scan parquet with pushdown filters + project columns (reduced IO)

Stage 2:
  Broadcast customers, join with orders (minimal shuffle)

Stage 3:
  Aggregation by segment (shuffle)

Stage 4:
  Write output partitions
```

Optimization objective:
- shrink Stage 1 input
- avoid unnecessary wide stages
- reduce Stage 3 skew/spill

## 4) Spark Internals (Basic → Moderate)

## Catalyst Optimizer
Catalyst applies:
- predicate pushdown
- constant folding
- column pruning
- projection/filter reordering

## Adaptive Query Execution (AQE)
At runtime Spark can:
- coalesce post-shuffle partitions
- handle skewed shuffle partitions
- switch join strategy (e.g., SMJ -> Broadcast)

## Tungsten + Whole-Stage Codegen
- optimized memory layout
- generated bytecode for operator pipelines
- reduced JVM object overhead

## Data Source Optimizations
For Parquet/ORC:
- min/max statistics pruning
- columnar reads
- vectorized execution paths

## 5) Real-World Scenario

**Netflix-style content analytics ETL**

Problem:
- 4-hour daily job violating SLA
- large joins + too many files + heavy shuffle

Fixes:
1. Added partition/date filters early (pushdown)
2. Selected only needed columns
3. Broadcasted small metadata dimensions
4. Enabled AQE and tuned shuffle partitions
5. Optimized output file count (~256MB target files)

Result:
- Runtime: 4h → 58m
- Cloud cost reduced ~60%
- Stable P95 runtime with fewer OOM incidents

## 6) Common Mistakes

1. Reading full table and filtering later.
2. Using Python UDF for logic available in native Spark SQL functions.
3. Caching huge DataFrames used only once.
4. Leaving default shuffle partitions for all workloads.
5. Ignoring small-file problem in output paths.
6. Not inspecting plan/UI and guessing optimization.

---

## 7) Performance Tips

- Use `df.explain("formatted")` before tuning.
- Push filters and project columns at source.
- Prefer built-in expressions over UDFs.
- Use broadcast joins for small dims.
- Tune partitions by data size (target partition ~128MB to 1GB depending workload).
- Write fewer, right-sized files.
- Reuse data? `cache/persist`; no reuse? avoid cache.
- Track:
  - shuffle read/write
  - spill bytes
  - skewed task runtime
  - GC time and executor utilization

### cache vs persist (must-know)
- `cache()` = shorthand for default memory storage level.
- `persist(level)` = explicit control (`MEMORY_ONLY`, `MEMORY_AND_DISK`, etc.)

### repartition vs coalesce (must-know)
- `repartition(n)` = full shuffle, rebalance, can increase/decrease partitions.
- `coalesce(n)` = reduce partitions with minimal shuffle (good near output write).

## 9) Optimization Playbook (Practical)

```text
1) Observe
   - Spark UI: stage time, skew, spill, shuffle.

2) Reduce data early
   - Filter + select before join/groupBy.

3) Pick join strategy
   - Broadcast small, handle skew keys.

4) Tune partitions
   - Correct shuffle partition count.
   - Repartition/coalesce intentionally.

5) Validate
   - Compare before/after runtime + cost + stability.
```

## 10) Global Cross-Coverage

- **How does Spark optimize queries?** Catalyst + AQE + data source pushdowns.
- **What happens during shuffle?** Partition exchange + network + disk + merge/sort.
- **How does Spark handle failures?** Task retries, stage retries, lineage recompute.
- **Why Spark over Hadoop?** In-memory DAG engine with optimized execution and fewer forced materialization steps.
